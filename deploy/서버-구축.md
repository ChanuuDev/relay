# Relay 원격 서버 구축·운영

Lightsail Ubuntu 24.04 한 대에 docker로 nginx·PostgreSQL 16·relay-api(NestJS)를 올린다. 접속 정보(IP·SSH 사용자·pem·토큰·비밀번호)는 이 문서와 깃에 적지 않는다. 실제 도메인은 Git에서 제외한 서버 `.env`의 `RELAY_DOMAIN`으로 관리한다. 이 문서의 `relay.example.com`은 예시다.

## 1. 처음 한 번: 호스트 준비

PC에서 (pem 경로와 호스트는 사용자가 안다):

```powershell
scp -i <pem> deploy/provision.sh <사용자>@<관리 호스트>:~/provision.sh
ssh -i <pem> <사용자>@<관리 호스트> bash ~/provision.sh
```

`provision.sh`가 하는 일: apt 갱신·무인 업그레이드, 시간대 Asia/Seoul, 스왑 2GB, ufw(22·80·443)·fail2ban, Docker Engine+Compose, 로그 회전, nvm+Node 22+pm2, uv, `/srv/relay`·`/srv/apps` 디렉터리, `secrets/pg_password`와 `.env`(없을 때만). 끝나면 **다시 로그인**해야 docker 그룹이 반영된다.

## 2. 처음 한 번: 설정 올리기와 인증서

```powershell
scp -i <pem> deploy/compose.yml deploy/backup.sh deploy/relay.sh deploy/install-cli.sh deploy/render-nginx.sh <사용자>@<관리 호스트>:/srv/relay/
scp -i <pem> deploy/nginx/conf.d/00-limits.conf deploy/nginx/conf.d/default.conf <사용자>@<관리 호스트>:/srv/relay/nginx/conf.d/
scp -i <pem> deploy/nginx/relay.http.conf <사용자>@<관리 호스트>:/srv/relay/nginx/relay.http.conf.template
scp -i <pem> deploy/nginx/relay.conf <사용자>@<관리 호스트>:/srv/relay/nginx/relay.conf.new
```

서버에서:

```bash
cd /srv/relay && chmod +x backup.sh
sudo sh /srv/relay/install-cli.sh
# 예시를 실제 서비스 도메인으로 바꾼다. 이 파일은 서버에만 보관한다.
printf '\nRELAY_DOMAIN=relay.example.com\n' >> .env
chmod 600 .env
sh ./render-nginx.sh nginx/relay.http.conf.template nginx/conf.d/relay.conf
RELAY_DOMAIN=$(sed -n 's/^RELAY_DOMAIN=//p' .env | tail -n 1)
# 1단계 nginx(80, ACME만)로 띄우고 인증서를 받는다. certbot 서비스의 entrypoint는 갱신 루프라 발급 때는 바꿔 부른다.
docker compose pull nginx postgres certbot
docker compose up -d --no-deps nginx
docker compose run --rm --no-deps --entrypoint certbot certbot certonly --webroot -w /var/www/certbot -d "$RELAY_DOMAIN" --register-unsafely-without-email --agree-tos --no-eff-email --non-interactive
# (메일을 받으려면 나중에: docker compose run --rm --no-deps --entrypoint certbot certbot update_account --email <메일>)
# 2단계 설정으로 바꾸고 다시 읽는다. certbot/conf/live는 root 소유라 sudo로 확인한다.
sh ./render-nginx.sh nginx/relay.conf.new nginx/relay.conf.new
sudo test -f "certbot/conf/live/$RELAY_DOMAIN/fullchain.pem" && mv nginx/relay.conf.new nginx/conf.d/relay.conf
docker compose exec nginx nginx -t && docker compose exec nginx nginx -s reload
docker compose up -d --no-deps certbot
```

갱신: certbot 컨테이너가 12시간마다 `renew`를 돈다. nginx가 새 인증서를 읽도록 cron에 `0 4 * * 1 cd /srv/relay && docker compose exec -T nginx nginx -s reload`를 둔다.

## 3. relay-api 첫 배포

이미지는 GitHub Actions(`deploy-server.yml`)가 GHCR(비공개)에 올리고 SSH로 `pull`·`up`한다. Actions Secrets: `DEPLOY_HOST`(관리 호스트명), `DEPLOY_USER`, `DEPLOY_KEY`(pem 내용). 서버의 GHCR 로그인은 그 실행의 `GITHUB_TOKEN`으로 그때만 하므로 서버에 장기 토큰이 남지 않는다.

Actions가 아직 돌지 않았거나 급할 때는 PC에서 직접 빌드해 올릴 수 있다:

```powershell
docker build -f server/Dockerfile -t relay-api:manual --build-arg RELAY_BUILD=manual .
docker save relay-api:manual | gzip | ssh -i <pem> <사용자>@<관리 호스트> "gunzip | docker load"
ssh -i <pem> <사용자>@<관리 호스트> "cd /srv/relay && grep -v '^RELAY_API_IMAGE=' .env > .env.next; echo RELAY_API_IMAGE=relay-api:manual >> .env.next; mv .env.next .env; chmod 600 .env; docker compose up -d"
```

첫 기동 때 기본 사용자(`RELAY_BOOTSTRAP_USER`)가 만들어진다. 기기 토큰:

```bash
relay create-token --name office-pc     # 어느 폴더에서든 실행. 토큰은 이때 한 번만 보인다
docker compose exec relay-api node dist/cli.js token list
docker compose exec relay-api node dist/cli.js token revoke <토큰 id>
```

`relay` 명령은 배포할 때 `/usr/local/bin/relay`에 설치·갱신됩니다. `--name`에는 기기를 구분할 이름을 넣으세요(공백이 있으면 따옴표 사용). `--json`을 붙이면 JSON으로 출력합니다. Docker 접근 권한이 없으면 `sudo relay create-token --name office-pc`로 실행하세요. 수동 설치는 `sudo sh /srv/relay/install-cli.sh`이며, 서버를 다른 폴더에 두었다면 `RELAY_SERVER_DIR`로 지정합니다. 기존의 다른 `relay` 명령은 덮어쓰지 않습니다.

확인: `curl -s "https://$RELAY_DOMAIN/api/v1/health"` → `"kind":"relay-remote"`. 바깥에서 5432는 닫혀 있어야 한다(`nc -zv <호스트> 5432` 실패).

## 4. 운영

| 일 | 명령 |
| --- | --- |
| 로그 | `docker compose logs -f relay-api` |
| 자원 | `docker stats`, `df -h`, `free -m` |
| 다시 띄우기 | `docker compose up -d` (이미지는 `.env`의 `RELAY_API_IMAGE`) |
| 이전 이미지로 되돌리기 | `.env`의 `RELAY_API_IMAGE` 태그를 바꾸고 `docker compose up -d relay-api` |
| 백업 | cron `0 3 * * * /srv/relay/backup.sh >> /srv/relay/backups/backup.log 2>&1` (pg_dump 14일, 파일 tar 주 1회 4주) |
| 복원 | `docker compose exec -T postgres pg_restore -U relay -d relay --clean --if-exists < backups/relay-YYYY-MM-DD.dump` |
| 디스크 경고 | `df -h /` 80% 넘으면 `backups/`와 `files/.trash` 확인 |
| 유지 작업 | relay-api가 매일 03:30(KST) 보관 기간 지난 세션·멱등 키·30일 지난 휴지통을 비운다 |

원격 파일 폴더는 `/srv/relay/files`(컨테이너의 `/data/files`)다. 컨테이너는 uid 1000(node)으로 돌고 호스트의 ubuntu도 uid 1000이라 그대로 읽고 쓴다.

## 4-1. 브라우저 모드 화면

relay.exe 없이 일반 브라우저로 원격 Relay를 쓰는 화면이다. 예시 도메인은 `relay-web.example.com`이고, 실제 값은 저장소 Secrets의 `RELAY_WEB_DOMAIN`과 서버 `.env`에만 둔다.

1. DNS: 화면 도메인의 A 레코드를 Relay 도메인과 같은 고정 IP로 둔다. 방화벽은 Relay와 같은 80·443이면 된다.
2. Secrets: `gh secret set RELAY_WEB_DOMAIN`으로 화면 도메인을 넣는다. 이 값이 없으면 배포는 화면을 건너뛴다.
3. 배포: Actions의 test 단계가 `npm run export:web -- dist/web --no-build`로 정적 화면을 만들어 `web.tgz`로 넘긴다. 서버의 `deploy-remote.sh`는 다음을 한다.
   - `web/releases/<태그>`에 풀고 `web/current` 링크만 바꾼다. 최근 3개만 남긴다. nginx는 `./web`을 `/srv/relay-web`으로 마운트한다.
   - `render-web-nginx.sh`로 `.env`에 `RELAY_WEB_DOMAIN`과 `RELAY_CORS_ORIGINS=https://<화면 도메인>`을 남긴다. relay-api는 이 출처에만 CORS를 연다.
   - 인증서가 없으면 1단계 설정(`relay-web.http.conf`, ACME만)으로 바꿔 webroot 방식으로 발급받는다. 그다음 2단계 설정(`relay-web.conf`)으로 바꾼다.
   - 끝나면 `https://<화면 도메인>/build.json`과 `/api/v1/health`를 확인한다.
4. 로그인: 화면을 열면 Relay 주소(기본값은 화면 출처)와 발급받은 토큰(`relay create-token --name <기기명>`)을 묻는다. 확인을 마치면 주소와 토큰을 AES-GCM으로 암호화해 localStorage에 둔다. 키는 꺼낼 수 없는 CryptoKey로 IndexedDB에만 둔다. 로그아웃하면 암호문과 키를 함께 지운다.

**PC 파일**: 파일 탐색기의 `이 PC` 자리에는 Relay가 원격 모드로 켜져 있는 PC의 파일이 보이고, `원격 서버` 드라이브에는 서버의 `/srv/relay/files`가 보인다. 브라우저는 그 PC에 직접 닿지 않는다. PC의 `relay web`(설치형 앱이 띄우는 것)이 `GET /api/v1/agent/next`로 서버에서 먼저 기다리다가 맡은 요청을 로컬 파일 API로 처리한다. 응답 바이트는 `POST /api/v1/agent/reply/:id`의 본문으로 흘려보내고, 서버는 그것을 브라우저 응답에 그대로 잇는다(`/api/v1/pcs/:기기/files…`). 그래서 공유기·방화벽에 포트를 열 필요가 없다. 볼 PC는 화면의 설정에서 고르고, 기본값은 지금 연결된 PC 중 가장 최근 것이다. 기본 앱으로 열기·시스템 클립보드·PC와 서버 사이 복사는 하지 않는다. 그 PC의 파일을 내보이지 않으려면 그 PC의 `~/.relay/config.json`에서 `remote.shareFiles`를 `false`로 두고 Relay를 다시 켠다. nginx는 두 경로를 버퍼 없이 넘기고, 요청 제한은 따로 둔다(`relay_pc`).

화면의 `/api/`는 nginx가 relay-api로 넘기고, 토큰은 브라우저가 `Authorization` 헤더로 붙인다. 쿠키는 쓰지 않는다. 그림·영상처럼 fetch를 거치지 않는 요청에는 서비스 워커(`sw-web.js`)가 토큰을 붙인다. 로그인 주소에 다른 Relay를 넣으면, 그 서버의 `RELAY_CORS_ORIGINS`에 이 화면의 출처가 있어야 한다.

## 5. 다른 프로젝트 올리기

`/srv/apps/<이름>/compose.yml`로 따로 띄우고, nginx에는 `/srv/relay/nginx/conf.d/<이름>.conf`에 `server_name <이름>relay.example.com` 블록을 더한 뒤 `nginx -s reload`한다. 같은 docker 네트워크를 쓰려면 relay의 네트워크(`relay_default`)에 붙인다. 인증서는 `docker compose run --rm certbot certonly --webroot -w /var/www/certbot -d <이름>relay.example.com`.

## 6. 알려진 제약

- 이미지가 약 560MB다. 루트 워크스페이스의 화면용 의존성까지 담겨서다. 나중에 server만의 lockfile이나 번들로 줄인다.
- RAM 2GB: PostgreSQL `shared_buffers=128MB`, `max_connections=40`. 프로젝트가 늘면 인스턴스를 키운다.

배포 스크립트는 기존 서버에 `RELAY_DOMAIN`이 없으면 현재 nginx 설정에서 읽어 비공개 `.env`로 이전한다. 서버 스크립트는 실제 도메인을 배포 로그에 출력하지 않는다.
